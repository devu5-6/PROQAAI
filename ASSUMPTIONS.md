# ASSUMPTIONS.md — Specification Ambiguities & Technical Resolutions

In real-world frontend engineering, specifications and project briefs often leave edge cases open. As part of this technical assessment, this document catalogues every ambiguity identified in the brief, the baseline assumption chosen to resolve it, and what would be confirmed with product and backend teams in a production environment.

---

## 1. Product & Scope Decisions

| # | Ambiguity in Specification | Chosen Assumption & Technical Resolution | What to Confirm with the Team |
|---|---|---|---|
| **1** | **Location Data Model**<br>The brief specifies a "live queue board for a location", but does not provide a location schema or selector. | Hardcoded the default location to ID `1` (`/api/locations/1/queue`). The API client is fully parameterized with `locationId` so adding a multi-location selector dropdown in the header is straightforward. | How many clinic locations exist, and does a single front-desk console ever need to manage multiple branches at once? |
| **2** | **Queue Taxonomy**<br>The number of queues and their exact names were not provided. | Modeled three realistic clinical queues: **General Intake**, **Vaccination Clinic**, and **Billing & Prescriptions**. | The official list of queues across clinics and whether queue types differ by location. |
| **3** | **Queue Placement When Moving Customers**<br>When moving a customer to another queue, should they be placed at the front, middle, or back? | Placed the moved customer at the **back** of the destination queue following standard First-In, First-Out (FIFO) queue principles. Their position number is recalculated accordingly. | Clinical triage policies: should urgent or re-triaged patients move to the front of the target queue, and should their wait timer reset upon transfer? |
| **4** | **Lifecycle of Completed / No-Show Customers**<br>What happens visually when a customer is marked "Served" or "No-Show"? | Completed and no-show customers leave the active queue board immediately to keep the screen uncluttered. A historical log tab was excluded to keep the console focused strictly on live operations. | Whether clinic staff need an instant "Undo" button or a dedicated "Completed Today" log to review past customer actions. |
| **5** | **Real-Time Delivery ("Near Real Time")**<br>The brief asks for near real-time updates without specifying WebSockets vs. polling. | Implemented **5-second polling** using TanStack Query. It automatically pauses polling when the browser tab is hidden to save network bandwidth and battery. WebSockets were deferred because polling is lightweight, highly reliable, and sufficient for clinic queue volume; TanStack Query can easily subscribe to a real WebSocket feed later. | Expected concurrent patient traffic and whether WebSocket infrastructure is available in the production backend. |
| **6** | **Mock Data Patterns**<br>The brief did not specify initial data volume or arrival behavior. | Seeded each queue with 3 to 9 realistic customer records and implemented a background simulation that adds a new walk-in every 12 to 27 seconds. This allows reviewers to observe non-jumping animations and table stability without manual input. | Real-world patient arrival patterns and daily peak-hour volume. |
| **7** | **Authentication & Role-Based Access**<br>No login or user permission requirements were outlined. | Omitted authentication entirely. The application assumes it runs on a trusted, shared workstation located behind the front desk. | Whether production deployment requires Single Sign-On (SSO), staff PIN codes, or role restrictions (e.g., only supervisors can reassign queues). |

## 2. User Experience (UX) & Interaction Decisions

| # | Ambiguity in Specification | Chosen Assumption & Technical Resolution | What to Confirm with the Team |
|---|---|---|---|
| **8** | **Customer Detail View Presentation**<br>The brief requires a detail panel that "opens without losing the queue view". | Built a **responsive side drawer**. On desktop screens (≥900px wide), the drawer opens side-by-side with the table in a split view. On tablet portrait screens (<900px), it slides over the table with an accessible backdrop. Full details in [UX_NOTES.md](file:///D:/practice/PROQAAI/UX_NOTES.md). | The exact tablet and monitor hardware models used by front-desk staff to ensure optimal physical ergonomics. |
| **9** | **The 14-Field Table Request**<br>The Product Manager asked to put all 14 customer fields directly into the table. | Kept 6 high-priority decision columns visible by default (`Position`, `Name`, `Status`, `Wait`, `Reason`, `Actions`), added a user-configurable column picker, and placed all 14 fields inside the 1-click detail drawer. This prevents unreadable text truncation and horizontal scrolling. | Review column usage data with the PM after launch to determine if certain optional columns should become default. |
| **10** | **Wait Time Severity Thresholds**<br>The brief did not define what wait time counts as "long". | Configured clear clinical thresholds in `src/lib/constants.ts`: **≥20 minutes** triggers a warning badge (amber with warning icon), and **≥40 minutes** triggers a critical alert badge (red with alert icon). | Clinic Service Level Agreements (SLAs), as some specialized clinics aim for under 15 minutes while others allow 30 minutes. |
| **11** | **Handling Multiple Waiting Patients in "Call Next"**<br>How should "Call Next" behave if patients are called out of order or absent? | "Call Next" identifies the first customer with status `"waiting"`, updates their status to `"called"`, and keeps them pinned at the top of the queue until staff mark them "Served" or "No-Show". | Whether a "called" patient should automatically expire back to "waiting" if staff do not complete the visit within a set time limit (e.g., 5 minutes). |
| **12** | **Multi-Desk Concurrency**<br>Can multiple desks manage the same queue simultaneously? | Supported implicitly via periodic background polling. Any actions taken on another computer sync to this screen on the next poll cycle. Action buttons guard against stale interactions. | Backend concurrency rules (e.g., server-side locking or conflict resolution if two staff members click "Call Next" at the exact same second). |

## 3. Technical & Architecture Decisions

| # | Ambiguity in Specification | Chosen Assumption & Technical Resolution | What to Confirm with the Team |
|---|---|---|---|
| **13** | **Mock API Technology**<br>The prompt suggested "MSW or something similar". | Selected **MSW v2 (Mock Service Worker)**. In the browser (development & production preview), it intercepts network calls via a Service Worker. In automated Vitest unit tests, it runs directly in Node.js. | Whether production API contracts are already documented so mock handlers can match exact production schemas. |
| **14** | **10% Random Failure Rate Application**<br>Which endpoints should simulate the ~10% failure rate? | Applied the 10% failure rate to both data fetching (GET requests automatically retry once) and mutations (which trigger optimistic rollbacks and toast notifications). Added custom headers (`x-force-success` and `x-force-failure`) to make automated tests 100% deterministic. | Whether GET requests failing 10% of the time is realistic, or if failures in production are predominantly confined to write operations. |
| **15** | **Failure Simulation During Live Demos**<br>Random 10% network failures make live reviewer demos unpredictable. | Maintained the specified 10% failure rate as the default, but added an environment variable `VITE_MOCK_FAILURE_RATE=0` in `.env.local`. This allows reviewers to run a completely clean demo or capture screenshots without modifying source code. | Whether interviewers prefer seeing simulated network rollbacks during the live walk-through or a quiet server demo. |
| **16** | **Browser Support Target**<br>Target browser versions were unspecified. | Targeted modern evergreen browsers (Chrome, Edge, Safari, Firefox) compiling to modern JavaScript (`ES2022`). Legacy browsers like Internet Explorer 11 are not supported. | Whether clinics operate specialized locked-down kiosk browsers or older legacy terminals. |
| **17** | **State Management Selection**<br>The brief permitted any state management approach if justified. | Adopted **TanStack Query** for asynchronous server state (polling, caching, cancellation, and optimistic rollbacks) and native React `useState` for purely local UI state (selected customer, visible columns). Heavy global state libraries like Redux were avoided to keep the architecture clean and maintainable. | Existing company conventions and preferred shared libraries. |
| **18** | **Static Cloud Deployment**<br>The brief noted a live deployed link is a plus, but provided no backend. | Configured as a static Single Page Application (SPA) compatible with Vercel and Netlify. Because production builds do not start the Service Worker by default, setting `VITE_ENABLE_MOCKS=true` in build environment settings activates MSW on the live demo site. Full deployment instructions are documented in [README.md](file:///D:/practice/PROQAAI/README.md). | The schedule for connecting the frontend application to an official staging backend. |
| **19** | **Time-Boxing Priorities (5–6 Hour Guideline)**<br>How to allocate time effectively within the recommended assessment limit? | Allocated time in strict order of importance: **1.** Data integrity & optimistic rollback correctness ➔ **2.** Stable, non-jumping table updates ➔ **3.** Comprehensive accessibility (a11y) ➔ **4.** Technical documentation. Storybook stories were included as an added bonus, keeping them lightweight rather than building a heavy visual regression suite. | Future sprint priorities when transitioning the prototype into a production feature. |
